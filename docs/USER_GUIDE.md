# User Guide

This guide runs the simulated Ledger Reconciliation Platform on macOS with JDK 17 and PostgreSQL 17. Use synthetic data only.

## Prerequisites

- Git
- JDK 17 (`java -version` must report 17)
- Either Homebrew PostgreSQL 17 or Docker Desktop with Docker Compose
- Port 5432 available for PostgreSQL and port 8080 available for the application

## Configure the Environment

Create the local, untracked configuration and replace both `change-this-*` password placeholders with secrets used only on this computer:

```sh
cp .env.example .env
chmod 600 .env
```

In `.env`, wrap each password value in single quotes. Keep each password on one line and do not include a single quote in the password itself. This format is interpreted consistently by the shell and Docker Compose.

The application does not read `.env` itself. Export its values before starting either database setup:

```sh
set -a
source .env
set +a
```

These assignments replace any stale `DB_*` or `APP_ADMIN_*` values in the current shell. Compose gives exported variables precedence over `.env`, so sourcing first ensures PostgreSQL and the Java application receive the same credentials. Do not commit `.env`; repeat the export commands in each new terminal.

Choose exactly one database setup below.

## Option A: Homebrew PostgreSQL

Install and start PostgreSQL 17:

```sh
brew install postgresql@17
brew services start postgresql@17
export PATH="$(brew --prefix postgresql@17)/bin:$PATH"
```

On a fresh Homebrew installation, create the application role and databases with the exported database password:

```sh
psql postgres -c "CREATE ROLE ledger_app WITH LOGIN PASSWORD '$DB_PASSWORD' CREATEDB;"
PGPASSWORD="$DB_PASSWORD" createdb -h localhost -U "$DB_USERNAME" --owner="$DB_USERNAME" ledger_platform
PGPASSWORD="$DB_PASSWORD" createdb -h localhost -U "$DB_USERNAME" --owner="$DB_USERNAME" ledger_platform_test
```

## Option B: Docker Compose

With the environment exported as described above, start PostgreSQL:

```sh
docker compose up -d
docker compose ps
```

After the database reports `healthy`, create the separate test database once:

```sh
docker compose exec db psql -U ledger_app -d ledger_platform -c 'CREATE DATABASE ledger_platform_test;'
```

Compose starts PostgreSQL only. The Java application continues to run on the host.

## Test, Package, and Run

The checked-in test profile has CI defaults. These overrides let local tests use the password from your `.env`:

```sh
SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/ledger_platform_test \
SPRING_DATASOURCE_USERNAME="$DB_USERNAME" \
SPRING_DATASOURCE_PASSWORD="$DB_PASSWORD" \
./mvnw test

SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/ledger_platform_test \
SPRING_DATASOURCE_USERNAME="$DB_USERNAME" \
SPRING_DATASOURCE_PASSWORD="$DB_PASSWORD" \
./mvnw package

./mvnw spring-boot:run
```

Alternatively, run the packaged executable JAR:

```sh
java -jar target/ledger-reconciliation-platform-0.1.0-SNAPSHOT.jar
```

## Use the Application

1. Open <http://localhost:8080/login> and sign in with `APP_ADMIN_USERNAME` and `APP_ADMIN_PASSWORD` from `.env`.
2. Open **客户账户**, choose **新建账户**, enter a synthetic owner name, and submit. The account number is generated by the application.
3. Open **资金操作**, choose **账户充值**, select an account, enter a positive amount in CNY cents and a unique idempotency key, then choose **提交充值**.
4. Choose **账户转账**, select different payer and payee accounts, enter a positive amount and a new idempotency key, then choose **提交转账**.
5. Return to **客户账户** to see balances derived from ledger entries.
6. Open **账本流水** to inspect the recent balanced journal transactions.
7. Open **自动对账** to import a synthetic channel statement and compare it with successful top-ups.

### Account Transfers

The transfer page is <http://localhost:8080/admin/payments/transfer>. Amounts are positive integers in CNY cents. Both accounts must exist, and the payer and payee must be different.

Each successful transfer creates one immutable, balanced ledger transaction with exactly two entries:

- `DEBIT` decreases the payer customer wallet.
- `CREDIT` increases the payee customer wallet by the same amount.

If the payer does not have enough available balance, the payment instruction is recorded as `FAILED` with the internal reason `INSUFFICIENT_FUNDS`, the page displays **付款账户余额不足**, and no ledger entries are written. A failed request is still idempotent: replaying the same key and payload returns the same failed instruction. After adding funds, submit a new transfer with a new idempotency key.

An idempotency key identifies the complete command, including operation type, payer, payee, amount, and currency. Reusing the key with the same data returns the original result without moving money again. Reusing it with different data is rejected.

Concurrent transfers from one payer acquire PostgreSQL locks in a stable account order. The balance is checked while those locks are held, so successful transfers cannot spend more than the starting balance and the payer **不能出现负余额**. There is no Redis, Kafka, or external lock service to configure.

Manual smoke test:

1. Create two synthetic customer accounts and note which one is the payer.
2. On **账户充值**, credit the payer with `10,000` cents using a unique key such as `smoke-topup-001`.
3. On **账户转账**, move `2,500` cents to the other account using `smoke-transfer-001`.
4. On **客户账户**, verify that the payer shows CNY 75.00 and the payee shows CNY 25.00.
5. On **账本流水**, verify a `TRANSFER` row for CNY 25.00. On either funding page, the recent history displays the Chinese type **转账** and status **成功**.
6. Submit more than the payer balance with a new key. Verify the Chinese insufficient-funds message, unchanged balances, and no new transfer row in the ledger.

Automatic reconciliation intentionally considers successful top-ups only; account transfers are internal wallet movements and are not channel statement candidates.

### Automatic Reconciliation

The reconciliation page is available to administrators from the **自动对账** navigation item. This milestone supports one synthetic channel, `SYNTHETIC_CHANNEL`, and a fixed UTF-8 CSV header:

```text
channel_transaction_id,amount_cents,occurred_at
```

Each data row contains a non-empty channel transaction ID, a positive amount in CNY cents, and an ISO-8601 timestamp. Uploads are limited to 2 MB and 10,000 data rows. The file is validated as a whole: if any row is invalid, the batch is marked `IMPORT_FAILED` and no statement details are stored.

After a successful upload, the batch is `IMPORTED`. Select **开始对账** to compare the statement with successful internal top-ups in the statement time range. The first version runs synchronously and produces four result types:

| 页面显示 | Internal status | Meaning |
| --- | --- | --- |
| 匹配一致 | `MATCHED` | Channel transaction ID and amount match an internal top-up. |
| 金额不一致 | `AMOUNT_MISMATCH` | The channel transaction ID exists internally, but amounts differ. |
| 仅渠道存在 | `CHANNEL_ONLY` | The statement contains a transaction with no matching internal top-up. |
| 仅内部存在 | `INTERNAL_ONLY` | A successful internal top-up has no matching statement row. |

The result list shows discrepancies first. An administrator can resolve an open discrepancy by entering a required note. The resolution records the administrator, timestamp, and note in a separate immutable history; resolving a discrepancy means **原支付和账本事实不会被修改**, and the imported channel statement remains unchanged. A matched result cannot be resolved.

The SHA-256 digest of the uploaded file provides idempotency. Uploading the same file again returns the existing batch instead of creating another one. A different file that repeats a channel transaction ID already imported in another batch is rejected, so the same channel event cannot be reconciled twice. A failed import can be retried with a corrected file; it has no statement details and cannot be started.

```sh
curl --fail http://localhost:8080/actuator/health
```

## Stop

Stop the Java process with `Ctrl-C`. Then stop only the database option you selected:

```sh
brew services stop postgresql@17
```

or:

```sh
docker compose stop
```

`docker compose stop` retains the named volume and its data.

## Reset Local Data

The following procedures are **destructive**. They permanently delete all application and test records. First verify that the exact targets are `ledger_platform` and `ledger_platform_test`; never substitute a production or shared database.

For Homebrew, list databases and confirm both names before dropping them:

```sh
PGPASSWORD="$DB_PASSWORD" psql -h localhost -U "$DB_USERNAME" -d postgres -l
PGPASSWORD="$DB_PASSWORD" dropdb -h localhost -U "$DB_USERNAME" ledger_platform_test
PGPASSWORD="$DB_PASSWORD" dropdb -h localhost -U "$DB_USERNAME" ledger_platform
PGPASSWORD="$DB_PASSWORD" createdb -h localhost -U "$DB_USERNAME" --owner="$DB_USERNAME" ledger_platform
PGPASSWORD="$DB_PASSWORD" createdb -h localhost -U "$DB_USERNAME" --owner="$DB_USERNAME" ledger_platform_test
```

For Docker Compose, run these read-only checks from this repository and confirm they show only this project and the `postgres-data` volume:

```sh
docker compose ls
docker compose ps
docker compose config --volumes
```

Only after confirming those targets, remove this Compose project's containers and named volume, then recreate them:

```sh
docker compose down --volumes
docker compose up -d
docker compose exec db psql -U "$DB_USERNAME" -d ledger_platform -c 'CREATE DATABASE ledger_platform_test;'
```

## Troubleshooting

- **Connection refused:** confirm PostgreSQL is running, port 5432 is free, and `DB_URL` names `localhost:5432/ledger_platform`. Use `docker compose ps` or `brew services list`.
- **Port already allocated:** stop the other PostgreSQL instance. Do not run Homebrew PostgreSQL and the Compose database on port 5432 at the same time.
- **Password authentication failed:** ensure the role password matches `DB_PASSWORD`. An existing Compose volume keeps the password from its first initialization; resetting the confirmed project volume is destructive but applies changed initialization credentials.
- **Database does not exist:** create `ledger_platform` for the application and `ledger_platform_test` for tests using the selected setup above.
- **`app.admin.username is required` or `app.admin.password is required`:** `.env` was not exported. Run `set -a; source .env; set +a` in the same terminal and restart the application.
- **Login fails after changing the admin password:** startup creates an admin only when the username is absent; it does not replace an existing password. Use the original local password or reset the confirmed local database if losing local data is acceptable.
