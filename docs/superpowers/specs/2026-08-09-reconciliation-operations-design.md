# 对账运营工作台设计（异步任务与异常闭环）

日期：2026-08-09

## 1. 背景

当前系统已经支持渠道 CSV 导入、手动运行精确对账、差异筛选，以及填写备注后直接将差异标记为已处理。现有实现能证明基础对账逻辑正确，但在面试演示时仍缺少两个关键能力：

- 对账执行是同步请求，无法展示后台任务、运行记录和失败重试过程。
- 差异只有 `OPEN -> RESOLVED` 的一步状态，无法展示认领、处理和操作时间线。

本阶段把现有功能升级为可演示的运营闭环，同时保持模块化单体和现有精确匹配规则。

## 2. 目标

1. 对账任务在后台异步运行，页面通过 HTMX 自动刷新任务状态。
2. 每次运行都保留独立尝试记录，包括请求人、状态、耗时、结果和失败原因。
3. 同一批次同一时间最多存在一个活动运行，重复点击不会重复执行。
4. 失败批次可以重试，新尝试不会覆盖旧尝试记录。
5. 差异形成可认领、可取消认领、可解决的工作项，并保存操作时间线。
6. 首页和异常工作台展示对面试演示有价值的运营指标。
7. 所有新增业务动作写入不可变审计日志。

## 3. 非目标

- 不拆分微服务，不引入消息队列或分布式任务框架。
- 不模拟第三方支付接口，不实现渠道定时拉取。
- 不增加金额容差、时间窗口或可配置规则引擎。
- 不通过对账处理自动修改账本或生成资金调整分录。
- 不实现多币种、多渠道或大数据量分片处理。
- 不显示无法真实计算的百分比进度；运行中只展示持久化状态和时间信息。

## 4. 方案选择

### 方案 A：异步运行记录和异常工单闭环（采用）

保留 CSV 和精确匹配，在现有 `reconciliation` 模块内增加运行尝试、异步调度、异常认领、处理结论和时间线。改动集中，能够直接形成可演示的业务闭环。

### 方案 B：先增加可配置匹配规则

可以体现规则设计，但当前演示数据较少，金额容差和时间窗口的视觉反馈有限，而且不能解决同步执行和异常状态过于简单的问题。

### 方案 C：模拟渠道接口和定时拉取

可以展示外部系统集成，但需要维护模拟服务、认证、重试和调度配置。大量代码只服务于模拟环境，不符合当前项目的最小完整范围。

## 5. 领域模型

### 5.1 对账批次

`ReconciliationBatch` 继续代表一份已导入渠道账单及其最新汇总状态。现有状态保持不变：

- `IMPORTED`
- `RUNNING`
- `COMPLETED`
- `IMPORT_FAILED`
- `RECONCILIATION_FAILED`

批次保存最终匹配数和差异数，但不再承担运行历史职责。

### 5.2 运行尝试

新增 `ReconciliationRun`，每次点击运行或重试创建一条记录：

- `id`
- `batchId`
- `attemptNumber`
- `status`: `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`
- `requestedBy`
- `requestedAt`
- `startedAt`
- `completedAt`
- `matchedRows`
- `differenceRows`
- `errorMessage`
- `version`

约束：

- `(batch_id, attempt_number)` 唯一。
- PostgreSQL 部分唯一索引保证每个批次最多一个 `QUEUED` 或 `RUNNING` 记录。
- 已结束运行记录不删除、不覆盖；重试创建更大的 `attemptNumber`。

状态转换：

```text
QUEUED -> RUNNING -> SUCCEEDED
                  -> FAILED
```

### 5.3 异常工作项

现有 `ReconciliationResult` 继续表示一条匹配结果。`MATCHED` 结果保持 `NOT_REQUIRED`；差异结果使用以下处理状态：

```text
OPEN -> CLAIMED -> RESOLVED
          |
          +-----> OPEN
```

新增字段：

- `assignedTo`
- `claimedAt`
- `version`

规则：

- 只有 `OPEN` 差异可以认领。
- 重复认领同一条已由本人认领的差异返回当前结果，不重复写事件。
- 已被其他管理员认领时返回冲突，不允许覆盖。
- 只有当前认领人可以取消认领或解决。
- `MATCHED` 和 `RESOLVED` 结果不能认领。
- 解决时必须选择处理结论并填写非空备注。

处理结论枚举：

- `INTERNAL_CONFIRMED`
- `CHANNEL_CONFIRMED`
- `IGNORED_TEST_DATA`
- `OTHER`

这些结论只记录运营判断，不自动修改账本。

### 5.4 异常事件

新增只追加的 `ReconciliationCaseEvent`：

- `id`
- `resultId`
- `action`: `CLAIMED`, `RELEASED`, `RESOLVED`
- `actor`
- `resolutionCode`，仅 `RESOLVED` 必填
- `note`，仅 `RESOLVED` 必填
- `createdAt`

数据库触发器拒绝 `UPDATE` 和 `DELETE`，确保页面时间线有不可变证据。现有已解决记录在迁移时回填一条 `RESOLVED` 事件。

## 6. 应用结构

所有代码继续位于 `reconciliation` 模块，不新增跨模块依赖。

### 6.1 API

`ReconciliationApi` 增加：

- `startRun(batchId, operator)`：创建或返回当前活动运行并提交后台执行。
- `findRuns(batchId)`：返回运行历史。
- `claim(resultId, operator)`：认领异常。
- `release(resultId, operator)`：取消本人认领。
- `resolve(resultId, resolutionCode, note, operator)`：解决本人认领的异常。
- `getResult(resultId)`：读取异常详情及时间线。
- `findCases(resultType, resolutionStatus, assignee)`：按结果类型、处理状态和负责人查询全局异常工作台；参数为 `null` 时不限制对应条件。
- `getOperationsSummary()`：提供首页指标。

现有同步 `run(batchId)` 和直接 `resolve(resultId, note, operator)` 被新接口替代，Web 层不再直接等待匹配执行完成。

### 6.2 异步执行

新增有界 `ThreadPoolTaskExecutor`，只用于对账任务。默认配置：

- core pool size: 2
- max pool size: 4
- queue capacity: 50
- thread name prefix: `reconciliation-`

启动流程：

1. Web 请求调用 `startRun`。
2. 独立事务锁定批次，校验状态并创建 `QUEUED` 运行记录。
3. 事务提交后把 `runId` 提交给执行器。
4. 后台线程在新事务中将运行和批次置为 `RUNNING`。
5. 读取渠道条目和成功充值，执行现有精确匹配。
6. 原子替换该批次结果，更新批次汇总，将运行置为 `SUCCEEDED`。
7. 任意运行时异常在独立事务中将批次和运行置为失败，并保存稳定错误信息。

执行器拒绝任务时，运行记录和批次立即进入失败状态。应用重启时，遗留 `QUEUED` 或 `RUNNING` 运行由启动恢复器标记为失败，管理员可以手动重试。此项目不声称提供跨进程任务续跑。

### 6.3 并发控制

- 启动任务时使用数据库行锁读取批次。
- 活动运行部分唯一索引作为最终并发保护。
- 两个并发启动请求返回同一活动运行，不创建重复尝试。
- 认领、取消认领和解决使用结果行锁及实体版本字段。
- 运行成功时，结果替换与批次汇总在同一事务完成。

认领、取消认领和解决分别使用 `RECONCILIATION_CASE_CLAIM`、`RECONCILIATION_CASE_RELEASE` 和 `RECONCILIATION_CASE_RESOLVE` 审计动作。后台运行完成或失败继续使用现有 `RECONCILIATION_RUN` 审计动作，并记录最初请求任务的管理员。

## 7. 页面设计

所有展示文本使用中文，状态值、类名、接口字段和数据库字段保持英文。

### 7.1 对账批次列表

- 保留导入入口。
- 增加最新运行状态、最近运行时间和异常处理进度。
- 失败批次突出失败原因，但不直接显示底层堆栈。

### 7.2 对账批次详情

- “开始对账”改为异步启动。
- `QUEUED` 或 `RUNNING` 时显示运行状态、请求人和开始时间。
- 使用 HTMX 每 2 秒获取状态片段。
- 运行结束后通过 `HX-Refresh` 刷新完整页面，停止轮询。
- 展示每次运行尝试的状态、耗时、匹配数、差异数和失败原因。

### 7.3 异常工作台

新增 `/admin/reconciliation/cases`：

- 默认只展示 `OPEN` 和 `CLAIMED` 差异。
- 支持按结果类型、处理状态和“只看我的”筛选。
- 展示渠道流水号、双方金额、差额、批次、负责人和发生时间。
- 每条记录进入独立异常详情页。

### 7.4 异常详情

- 展示渠道金额、内部金额、差额、结果类型和来源批次。
- `OPEN` 状态显示“认领”。
- 本人认领后显示“取消认领”和解决表单。
- 解决表单使用处理结论下拉选项和备注输入框。
- 展示不可变操作时间线。

### 7.5 经营概览

增加以下指标：

- 最近已完成批次匹配率。
- 待认领异常数。
- 处理中异常数。
- 失败对账任务数。

不增加装饰性图表，指标直接链接到相关批次或异常工作台。

## 8. 错误处理

- 非法状态转换返回业务校验错误，Web 层显示中文提示。
- 并发认领冲突返回“该异常已被其他管理员认领”。
- 后台异常只保存异常类型和最长 2000 字符的稳定消息。
- 重复启动返回活动运行，不显示重复成功提示。
- 已解决异常的重复解决不会生成第二条解决记录或事件。
- 页面参数中的非法枚举返回 `400`，不回退为无筛选。

## 9. 数据库迁移

新增 Flyway `V12`，负责：

1. 创建 `reconciliation_run` 和活动运行部分唯一索引。
2. 为 `reconciliation_result` 增加负责人、认领时间和版本字段。
3. 扩展处理状态约束以允许 `CLAIMED`。
4. 为 `reconciliation_resolution` 增加处理结论，并为历史记录填充 `OTHER`。
5. 创建 `reconciliation_case_event`、查询索引和禁止更新删除的触发器。
6. 为历史已解决结果回填负责人、认领时间和解决事件。

迁移必须同时通过空库安装和 V11 升级路径测试。

## 11. 演示路径

1. 创建账户并完成一笔充值。
2. 导入包含匹配、金额不一致和仅渠道记录的 CSV。
3. 点击开始对账，页面显示后台运行状态并自动刷新。
4. 查看运行历史和汇总结果。
5. 打开异常工作台，认领一条差异。
6. 选择处理结论、填写备注并解决。
7. 查看异常时间线和全局审计日志。
8. 展示首页匹配率和待处理指标变化。
